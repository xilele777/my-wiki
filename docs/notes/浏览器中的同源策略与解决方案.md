---
title: 浏览器中的同源策略与解决方案
---
理解同源策略（Same-Origin Policy），你只需要记住一句话：

> **“不同源的网站之间，浏览器不允许随意‘串门’拿东西，除非对方明确开了门禁。”**

这就像两栋独立的公寓楼（不同的源）。A楼的住户（网页）不能随便去B楼住户家里翻抽屉（读Cookie、操作DOM），更不能冒充B楼住户去刷卡（发请求）。这就是浏览器安全的**基石**，用来防止恶意网站窃取你的隐私数据（比如银行账户信息）。

下面我分**核心定义**、**限制了什么**、以及**三大终极解决方案**三部分来拆解。

---

### 1. “同源”到底指什么？

**源（Origin）** = **协议（Protocol）** + **域名（Domain）** + **端口（Port）**。三者必须**完全一致**才叫同源。

| 对比地址 A | 对比地址 B | 是否同源？ | 原因 |
| :--- | :--- | :--- | :--- |
| `https://abc.com` | `https://abc.com` |  是 | 协议、域名、端口全一致 |
| `http://abc.com` | `https://abc.com` |  否 | 协议不同（http vs https） |
| `https://abc.com` | `https://www.abc.com` |  否 | 域名不同（abc.com vs www.abc.com） |
| `https://abc.com:443` | `https://abc.com:8080` |  否 | 端口不同（443 vs 8080） |

---

### 2. 同源策略到底“管”什么？（三个禁区）

浏览器会拦截以下三种跨源行为：

1. **网络请求（最常用）**：跨域的 AJAX / Fetch 请求被浏览器拦截（注意：请求其实发出去了，但浏览器拒收返回结果）。
2. **DOM 访问**：不能跨域操作另一个页面中的 DOM（比如 `iframe` 嵌入的外站页面，你拿不到里面的内容）。
3. **存储访问**：不能跨域读取 Cookie、LocalStorage、IndexDB。

---

### 3. 跨域解决方案（3 大主流 + 2 个特殊场景）

针对最常见的**跨域网络请求**，有以下成熟方案。按推荐优先级排序：

####  方案一：CORS（跨域资源共享）—— 现代标准，首选
**核心思想**：后端服务器在响应头里加一个“白名单”字段，告诉浏览器：“这个来源我认识，放行！”

服务端需设置响应头（以 Node.js/Express 为例）：
```javascript
// 允许特定的源（* 代表所有，但携带 Cookie 时不能为 *）
res.setHeader('Access-Control-Allow-Origin', 'https://your-frontend.com');
// 允许的请求方法
res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE');
// 允许携带 Cookie（如果需要）
res.setHeader('Access-Control-Allow-Credentials', 'true');
```

> **重要提示（面试高频）**：CORS 会把请求分为两类：
> - **简单请求**（GET/HEAD/POST，且 Content-Type 为 `text/plain` 等）：直接发送，浏览器看响应头放行。
> - **非简单请求**（如 PUT 方法，或 Content-Type: `application/json`）：**先发一个 OPTIONS 预检请求（Preflight）**，询问服务器是否允许，服务器说“可以”后，才发真正的请求。

####  方案二：代理服务器（Proxy）—— 前端最常用（Vue/React 开发环境）
**核心思想**：同源策略**只针对浏览器**，服务器之间没有跨域限制。让前端请求同源的代理服务器，代理服务器再去请求目标服务器，把结果转发回来。

- **开发环境**（Webpack/Vite）：配置 `devServer.proxy`。
  ```javascript
  // vite.config.ts
  export default {
    server: {
      proxy: {
        '/api': 'https://target-server.com' // 请求 /api/xxx 会被转发
      }
    }
  }
  ```
- **生产环境**：使用 **Nginx 反向代理**，配置 `location` 转发请求。

####  方案三：JSONP（仅限 GET 请求）—— 古董级但经典
**核心思想**：`<script>`、`<img>`、`<link>` 标签不受同源策略限制。利用 `<script src="跨域接口?callback=fn">`，服务器返回一段执行 `fn(data)` 的 JS 代码。

```javascript
// 前端定义回调函数
function handleData(data) { console.log(data); }
// 动态创建 script 标签，将函数名传给后端
const script = document.createElement('script');
script.src = 'http://api.com/user?callback=handleData';
document.body.appendChild(script);
// 后端返回: handleData({ name: 'Alice' })
```
> **缺点**：只能 GET，无法处理错误，现已基本被 CORS 取代。

### 4. 两个特殊场景解决方案（非网络请求）

####  场景：主域相同，子域不同（如 `a.abc.com` 和 `b.abc.com`）
- **解决方案**：在两个页面中设置 `document.domain = 'abc.com'`。浏览器会认为它们降级成了同一个源（仅限同主域，且端口均为 null）。

####  场景：页面与嵌入的 iframe 跨域通信
- **解决方案**：使用 **`window.postMessage`** API。这是 HTML5 提供的跨文档消息传递机制，安全可控。
```javascript
// 父页面发送消息
iframe.contentWindow.postMessage('hello', 'https://child.com');
// 子页面监听
window.addEventListener('message', (e) => {
  if (e.origin === 'https://parent.com') { // 一定要校验来源！
    console.log(e.data);
  }
});
```

---

###  一句话总结（面试回答模板）

> “同源策略是浏览器安全的基石，限制跨域读写 DOM 和发请求。**解决跨域最推荐 CORS**，由后端设置 `Access-Control-Allow-Origin` 响应头；**开发调试用代理 Proxy**；**老旧系统或仅 GET 用 JSONP**；**跨窗口通信用 postMessage**。记住，跨域请求能发出但被浏览器拦截，所以本质上需要**后端配合**。”
